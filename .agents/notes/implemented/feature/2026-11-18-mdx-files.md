# Agent Note: MDX files

Status: implemented — MDX uses the existing Markdown file and editing paths

## Problem

MDX blog posts must be available in workspace listings, search, recent files
and single-file opens. Extension checks spread across these paths can disagree.

## Decision

`apps/desktop/shared/markdown-extensions.json` owns supported extensions.
Frontend path helpers and Rust's extension-only `open_target::is_markdown`
read this registry. The watcher recognizes removed paths without filesystem
metadata. Bundle association tests check the static Tauri and macOS declarations.

MDX uses the Markdown editor and save path. Imports, JSX and expressions stay
source text. Wiki links prefer an explicit extension and retain it when files
in the same folder share a stem. Ambiguous root targets start with `./` to
resolve within the workspace root. Existing stem fallback remains available.

## Alternatives considered

- Add MDX to each existing extension check. This leaves sidebar, watcher and
  open behavior free to diverge.
- Compile MDX and load project components. Editing blog prose needs file
  recognition; component execution adds dependencies and project configuration.

## Consequences

MDX follows Markdown's workspace, autosave and external-change behavior.
The editor does not preview project components. Tests cover source preservation,
MDX-only folders, mixed extensions, search, recents, link collisions and bundle
associations. The static bundle declarations still need explicit updates when
adding an extension; their consistency test catches omissions.
